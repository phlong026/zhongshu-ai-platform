## 2. 一期目标

一期不是一次性建设全部业务域，而是先形成一个可持续接入业务模块的技术底座。

一期目标包括：

1. 建立独立的众墅之家产品工程和可追溯的上游代码基线；
2. 使用 PostgreSQL 作为唯一核心关系数据库；
3. 建立 Web 与小程序/移动端的唯一主工程；
4. 建立账号、身份、组织、租户、角色、菜单、动作、数据范围和审计基础；
5. 建立 System、Infra、文件、消息、任务、日志等通用能力；
6. 验证 PostgreSQL 下的初始化、事务、ID、Quartz、分页、批量清理和代码生成；
7. 为首条薄纵向业务链提供可运行的权限、流程、状态和审计承载能力；
8. 建立文档、需求、迁移、测试和实施结果的同步门禁。

### 2.1 一期成功标准

只有同时满足以下条件，才能称为“一期底座完成”：

- 固定并记录 RuoYi-Vue-Pro JDK 17 上游 commit SHA；
- 后端、Web、小程序主工程能够在新项目目录中独立构建；
- PostgreSQL 空库可以通过版本化迁移重复初始化；
- System、Infra、Quartz、登录、租户、权限、文件、日志和 Token 清理在真实 PostgreSQL 上通过；
- 至少两个测试组织完成横向隔离验证；
- 权限判定由服务端执行，客户端伪造组织和动作参数无效；
- 关键操作有可查询的审计记录；
- 所有已实现需求都有测试或明确的人工验收证据；
- README、复用方案、本文档与实际实现保持同步；
- 本地验证、部署结果、真实角色 UAT 和生产放行分别记录，不混为一个状态。

- Vue3 主工程；
- 登录、退出、用户信息；
- 动态菜单和路由；
- 菜单/按钮权限；
- 服务端确认的组织/身份上下文入口；仅在 D-09 确认支持多身份时提供身份切换；
- System、Infra 和基础组织权限管理页面；
- 一期纵向链所需的最少角色页面。

#### 小程序/移动端

- Admin UniApp 主工程；
- 登录态、请求、路由、上传和通用组件；
- 服务端导航和角色工作台容器；
- 一期纵向链所需的最少员工/负责人页面。

#### 数据与质量

- PostgreSQL 独立数据库和低权限运行账号；
- 从第一版开始执行版本化数据库迁移；
- PostgreSQL 集成测试环境；
- 租户隔离、对象授权、文件访问、日志清理、Token 清理和并发幂等测试；
- 文档与实现同步检查。

- 完整 CRM、Mall、ERP、WMS、Pay 模块整体迁入；

### 5.2 PostgreSQL

| 需求编号 | 需求 | 验收条件 |
|---|---|---|
| FND-DB-001 | PostgreSQL 是唯一关系数据库基线 | 开发、自动化测试和部署配置不依赖 MySQL 实例 |
| FND-DB-002 | 使用项目独立数据库 | 不与其他项目共用业务数据库；数据库名称和用途有记录 |
| FND-DB-003 | 运行账号不得使用超级管理员 | 应用账号只拥有运行所需最小权限；迁移权限与运行权限可追踪 |
| FND-DB-004 | PostgreSQL 主版本必须固定 | 优先 17、可接受 16；本地服务器实际版本核验后写入环境说明 |
| FND-DB-005 | 数据库变更必须版本化 | 建表、索引、约束、数据回填和回滚均有有序迁移记录 |
| FND-DB-006 | 空库初始化必须可重复 | 在全新数据库上可重复执行，并得到一致结构和基础数据 |
| FND-DB-007 | 不允许 MySQL 专用 SQL 混入 | 静态扫描和真实 PostgreSQL 测试覆盖常见 MySQL 方言 |
| FND-DB-008 | 已知清理任务必须适配 | 访问日志、错误日志、任务日志、Access Token、Refresh Token 批量清理在 PostgreSQL 上通过 |
| FND-DB-009 | Quartz 必须使用 PostgreSQL 表和方言 | 定时任务创建、执行、并发和清理通过真实 PostgreSQL 验证 |
| FND-DB-010 | 代码生成器必须读取 PostgreSQL 元数据 | 表、列、主键、类型、注释和索引识别结果正确 |
| FND-DB-011 | 时间、布尔、长文本和 JSON 映射必须统一 | Java 与 PostgreSQL 的读写、排序、筛选和序列化结果可预测 |
| FND-DB-012 | 索引必须围绕真实查询设计 | 租户、组织、状态、创建时间、业务键等高频条件具备必要索引 |

迁入时已知的 5 处 `DELETE ... LIMIT` 已在本轮改成稳定有界子查询，并通过真实PG回归；对应源码为：

- `JobLogMapper.deleteByCreateTimeLt(...)`；
- `ApiAccessLogMapper.deleteByCreateTimeLt(...)`；
- `ApiErrorLogMapper.deleteByCreateTimeLt(...)`；
- `OAuth2AccessTokenMapper.deleteByExpiresTimeLt(...)`；
- `OAuth2RefreshTokenMapper.deleteByExpiresTimeLt(...)`。

这些阻断点必须先有 PostgreSQL 失败测试，再改为可移植的批量删除实现。仅修改连接地址不算完成 PostgreSQL 适配。

## 6. 首条薄纵向业务链建议（D-07）

### 6.1 建议名称

**加盟商开通—首条线索闭环**

### 6.2 选择原因

该链路不是为了提前开发完整销售系统，而是用最少业务对象验证底座是否真的支持：

- 平台、加盟商负责人、加盟商员工三个角色；
- 账号、身份、组织、租户和数据范围；
- 资质附件和文件权限；
- Flowable 审批；
- 服务端导航和角色工作台；
- 消息、任务、审计和幂等；
- 一条从创建到结束的业务状态机。

### 6.3 建议流程

1. 平台运营创建或受理加盟商开通申请；
2. 加盟商提交基本信息和资质附件；
3. 平台负责人审批通过或拒绝；
4. 审批通过后，系统幂等创建加盟商组织、负责人身份和默认授权；
5. 加盟商负责人登录并新增员工身份；
6. 平台运营向该加盟商下发一条线索；
7. 加盟商负责人将线索分配给员工；
8. 员工领取并提交跟进记录；
9. 线索转为有效商机，或以明确原因关闭为无效；
10. 负责人和平台人员按授权查看结果与完整审计记录。

### 6.4 建议最小状态

以下状态仅是建议，D-07 确认前不得视为最终业务规则：

| 对象 | 建议状态 |
|---|---|
| 加盟商申请 | `DRAFT`、`PENDING_APPROVAL`、`APPROVED`、`REJECTED`、`CANCELLED` |
| 组织/身份 | `PENDING_ACTIVATION`、`ACTIVE`、`DISABLED`、`EXPIRED` |
| 线索 | `NEW`、`ASSIGNED`、`CLAIMED`、`FOLLOWING`、`CONVERTED`、`INVALID` |

### 6.5 D-07 确认前允许和禁止的工作

允许：

- 固定底座源码；
- PostgreSQL 适配；
- System、Infra、登录、租户和权限基础建设；
- 编写业务链验收测试草案。

禁止：

- 固化加盟商申请字段；
- 固化线索状态和流转条件；
- 实现自动分配、奖励、报价、合同或回款规则；
- 把建议状态写成不可逆数据库约束。

## 9. 验收状态定义

### 9.1 状态含义

为避免“代码写完”等同于“已经上线”，统一使用以下状态：

| 状态 | 含义 |
|---|---|
| `DOCUMENTED` | 已写入需求或设计，还没有实现证据 |
| `IMPLEMENTED` | 代码已实现，但验证可能不完整 |
| `LOCALLY_VERIFIED` | 本地静态检查、测试和必要浏览器验证通过 |
| `CI_VERIFIED` | 远程 CI 在固定提交上通过 |
| `DEPLOYED` | 已部署到指定环境，并记录版本和配置 |
| `UAT_ACCEPTED` | 真实角色按业务清单完成人工验收 |
| `PRODUCTION_GO` | 外部集成、备份、监控、回滚和业务负责人共同放行 |

文档更新本身只能达到 `DOCUMENTED`，不能据此声称 PostgreSQL、底座或业务链已经运行。

## 10. 文档同步与变更控制

本章是 `FND-DOC-001～003` 的执行规则。2026-10-11已恢复本地机械检查并重新验证；语义评审、运行能力及远程CI通过仍需各自证据，不能由检查器存在推导。

### 10.1 必须同步的文件

任何涉及以下内容的决策或实现变更，都必须同时检查并更新：

1. `README.md`：阶段、状态、文档索引；
2. `docs/01-底座代码复用与改造方案.md`：架构理由、复用边界、决策快照；
3. 本文档：需求、验收、决策台账、阻塞关系；
4. 后续产生的 API、数据库、测试和部署文档。

### 10.2 触发同步的变更

- 框架、JDK、数据库、前端或流程引擎发生变化；
- 模块从关闭变为启用，或从一期移出；
- 账号、身份、组织、权限和租户模型变化；
- 业务链、状态机、字段、角色、动作或数据范围变化；
- 新增或取消外部集成；
- 验收状态从文档、实现、本地验证、部署、UAT 到生产放行发生变化；
- 已知风险被修复、接受或新增。

### 10.3 同步完成门禁

一次变更只有满足以下条件才算完成：

- 相关文档中的同一决策编号状态一致；
- 不再出现已废弃技术选型，例如“核心数据库仍待确认 MySQL”；
- README 能在两次点击内到达最新需求和方案；
- 文档中的版本、日期、范围和状态已更新；
- 代码行为与需求不一致时，不能以代码为准静默覆盖文档；必须先明确决策并同步；
- 第 9.3 节已登记所有状态发生变化的需求，并分开记录代码/迁移、自动化测试、外部集成/UAT/部署证据；
- 本地文档一致性检查通过；CI 建立后，同一检查在固定提交上通过；
- 提交说明列出本次同步更新的文档和仍未决事项。

### 10.4 自动检查最小契约

阶段 0 建立的检查器至少必须验证：

1. README 文档索引版本与两份文档页首版本、最新变更记录一致；
2. D-01～D-11 在 README、复用方案和本文档中的状态与阶段门禁不冲突；
3. Markdown 相对链接能够解析到存在的文件；
4. `FND-*`、`PILOT-REQ-*` 和 `PEND-*` 编号唯一，追踪矩阵引用的编号存在；
5. 任何高于 `DOCUMENTED` 的 FND 需求都存在第 9.3 节证据行，且证据类型与所声明状态匹配；
6. 已废弃或未确认的技术/业务规则没有被写成当前事实，例如把 D-09 尚未确认的多身份切换写成无条件范围。

本地和 CI 必须调用同一套检查逻辑，避免两套规则漂移。只有真实 CI 在固定提交上通过时，才允许记录 `CI_VERIFIED`。
